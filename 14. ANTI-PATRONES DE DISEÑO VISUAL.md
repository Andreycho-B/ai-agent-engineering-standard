# 14. ANTI-PATRONES DE DISEÑO VISUAL

**Versión:** 2.2  
**Estado:** Normativo  
**Jerarquía:** Nivel 3 (Especializaciones)

---

## Propósito

Define el criterio que un agente debe aplicar para evitar interfaces genéricas, repetitivas o identificables como generadas por IA. No fija un estilo visual, no promueve una tendencia y no impone una escuela de diseño: define cuándo una decisión visual está justificada y cuándo es un reflejo automático heredado de los datos de entrenamiento. Toda decisión visual debe responder a una intención funcional, editorial o de marca — nunca únicamente estética.

Este documento se integra con el **Protocolo Operativo (01)** (donde se aplican las decisiones de diseño), la **Conciencia del Proyecto (09)** (para alinear el diseño con la identidad del proyecto), la **IA Generativa (13)** (para reconocer sesgos visuales), los **Principios de Ingeniería Avanzada (23)** (para evitar sobreingeniería visual) y el **Sistema de Auditoría (25)** (para verificar el diseño final).

---

## Prioridad operativa

Las reglas se clasifican según su exigencia:

- **CRÍTICA** — requiere justificación explícita y verificable antes de romper la regla (una de las excepciones generales, o una razón equivalente que el agente pueda enunciar). No basta con "se ve mejor así".
- **ALTA** — requiere una razón de diseño razonable, pero no necesita documentarse con el mismo rigor que una CRÍTICA.
- **MEDIA** — puede ajustarse por criterio de diseño en el momento, sin necesidad de justificación explícita, siempre que no contradiga una regla CRÍTICA o ALTA relacionada.

---

## Excepciones generales

Todas las reglas de este capítulo están activas por defecto y solo se suspenden cuando ocurre alguna de estas condiciones: el usuario solicita explícitamente un estilo determinado; el proyecto ya dispone de un Design System compatible; existe una justificación funcional, editorial, de marca o técnica verificable; la restricción produce una mejora objetiva de accesibilidad; o mantenerla produce un resultado objetivamente inferior. Fuera de estos casos, la regla se respeta.

---

### A. La estructura nace del contenido, nunca de una plantilla

**Núcleo:** Cada interfaz se construye a partir de su contenido, sus objetivos y su contexto específico. Un agente nunca debe reutilizar automáticamente una estructura mental aprendida, por más veces que esa estructura haya funcionado en otro proyecto.

**Justificación:** La repetición sistemática de estructuras produce interfaces previsibles, y esa previsibilidad es precisamente lo que hace que una interfaz se reconozca como generada por IA. El ejemplo más notorio es el "layout universal" de landing page: Hero, cinta de logos, características, métricas, cards, testimonios, FAQ, CTA, footer — repetido sin importar el producto.

| Patrón a evitar | Regla específica | Excepciones |
| :--- | :--- | :--- |
| Layout universal de landing (Hero→Logos→Cards→Métricas→Testimonios→FAQ→CTA) | La estructura de la página surge de los objetivos del proyecto, no de una plantilla aprendida | Solicitud expresa del usuario de una landing SaaS tradicional; el proyecto ya reutiliza esa estructura deliberadamente |
| Grid automático de tres columnas para cualquier contenido | No asumir que todo contenido se distribuye en tres columnas por defecto | Ninguna sin justificación de contenido |
| Hero como primer bloque obligatorio | El Hero existe solo cuando aporta una introducción significativa; no es un requisito estructural | Páginas donde el usuario pida explícitamente ese formato |
| Hero sobredimensionado que obliga a hacer scroll para llegar a contenido útil | El Hero comunica rápido; no ocupa espacio solo para existir | — |
| Secciones que parecen diapositivas apiladas, sin relación visual entre ellas | La interfaz transmite continuidad; las secciones se relacionan entre sí | — |
| La Card (o cualquier contenedor) se diseña antes que el contenido que va a llevar | Primero existe el contenido; después la estructura necesaria para comunicarlo | — |

**Verificación:** Antes de fijar una estructura, preguntarse: ¿estoy resolviendo este contenido específico o reutilizando el mismo esqueleto de siempre? Y, sección por sección: si esta sección desaparece, ¿se rompe realmente la comunicación de la página? Si no, probablemente nunca fue necesaria.

---

### B. Todo elemento visual debe justificar su función

**Núcleo:** Ningún elemento visual existe solo porque aparece con frecuencia en los datos de entrenamiento o porque está de moda. Todo elemento debe justificar su existencia mediante comprensión, navegación, identidad, jerarquía o interacción.

**Justificación:** Cada elemento sin función incrementa el ruido visual y desplaza la atención de lo que sí comunica. La adopción rápida de modas visuales como si fueran estándares permanentes es, además, una de las formas más fáciles de identificar una interfaz como generada por IA.

| Patrón a evitar | Regla específica | Excepciones |
| :--- | :--- | :--- |
| Contenedores que existen solo para "dar sensación de diseño" | Todo contenedor justifica agrupación lógica, interacción, navegación u organización | — |
| Chips o pills usados porque están de moda, no porque representen estados, filtros, categorías o acciones reales | Los chips representan datos funcionales, no decoración | — |
| Cards con borde, sombra, blur, gradiente, glow, transparencia y ruido simultáneos | Cada recurso visual tiene una función; no se acumulan efectos sobre un mismo elemento | — |
| Iconos añadidos para que una sección "parezca más completa" | Los iconos complementan la comprensión; nunca sustituyen información real | — |
| Glassmorphism, glow, gradientes, mesh gradients, aurora backgrounds, noise, blobs, SVG decorativos aplicados por default | Todo recurso responde al lenguaje gráfico del proyecto, no a una tendencia | — |
| Componentes añadidos porque se han visto repetidos en Awwwards, Dribbble o Figma Community | Cada componente justifica objetivamente su existencia; se diseña para comunicar, no para impresionar | — |
| Adopción de una tendencia visual como si fuera un estándar permanente | Toda decisión estética se justifica por el proyecto, nunca únicamente por ser tendencia | — |

**Verificación:** Si el elemento desaparece y la interfaz sigue comunicando correctamente, probablemente no era necesario. Pregunta de control para tendencias: ¿seguiría tomando esta decisión si esta moda nunca hubiera existido? Cuando el elemento corresponda a una estética reconocible de IA, aplica además la familia N.

---

### C. Prohibido inventar datos o prueba social

**Núcleo:** Ninguna métrica, testimonio o logo puede fabricarse para rellenar una interfaz. Si el dato real no existe, la sección se pide, se marca como placeholder identificado, o se elimina — nunca se inventa.

**Justificación:** Las reglas de esta familia estaban duplicadas en el original (tres variantes de "no inventes métricas"). Se consolidan aquí junto con testimonios y logos falsos, que son la misma prohibición aplicada a otro tipo de contenido.

| Patrón a evitar | Regla específica | Excepciones |
| :--- | :--- | :--- |
| Métricas decorativas sin dato real detrás (500+, 95%, 120K, 24/7) | Las métricas aparecen solo cuando hay información verificable; nunca se inventan ni se usan como relleno visual | Dashboards, analítica, sistemas BI, informes — donde el propio sistema puede generar la cifra real |
| Testimonios de personas o empresas ficticias | Prohibido generar testimonios falsos | Ninguna — la alternativa es pedir testimonios reales, usar un placeholder identificado como tal, o eliminar la sección |
| Cintas de logos de clientes o partners inventados | Las cintas de logos aparecen solo cuando aportan credibilidad verificable | Clientes, partners, patrocinadores o marcas reales; solicitud explícita del usuario |

**Verificación:** Ante cualquier cifra o nombre propio en la interfaz: ¿existe una fuente real detrás, o se generó para que la sección "se viera completa"? Si es lo segundo, se elimina.

---

### D. La repetición y el uso de tarjetas responden a necesidad, no a automatismo

**Núcleo:** Convertir todo en Cards, repetir el mismo bloque veinte veces, o encapsular cada párrafo en su propio contenedor no es un default aceptable. La repetición y el uso de tarjetas se justifican solo cuando existe una separación conceptual real entre los elementos.

**Justificación:** El exceso de tarjetas rompe el flujo de lectura y produce una estética fácilmente reconocible como generada por IA — decenas de cajas con el mismo aspecto visual, cada una añadiendo padding, sombra y borde sin aportar jerarquía real.

| Patrón a evitar | Regla específica | Excepciones |
| :--- | :--- | :--- |
| Convertir toda la interfaz en un conjunto de Cards | Las Cards se usan solo cuando hay separación conceptual real entre elementos | Dashboards, paneles administrativos, sistemas de monitorización, galerías, catálogos, solicitud del usuario |
| Cards anidadas dentro de Cards | No anidar contenedores salvo jerarquía funcional claramente diferenciada | — |
| Transformar cualquier tipo de contenido (artículos, ensayos, documentación) en pequeños paneles tipo widget | Cada tipo de contenido mantiene su naturaleza; no todo se convierte en panel informativo | — |
| El mismo bloque (icono, título, texto, botón) repetido veinte veces sin variación | Cuando varias tarjetas comparten exactamente la misma estructura, evaluar si existe una forma más adecuada de presentar la información | — |
| Contenedor individual para cada párrafo de texto simple | El texto continuo se mantiene en el flujo editorial salvo razón funcional para separarlo | — |
| Repetición mecánica de un mismo patrón (misma card, mismo espaciado, misma altura, mismo icono) en toda la interfaz | La repetición solo existe cuando mejora la comprensión, no como mecanismo automático de composición | — |

**Verificación:** Eliminar los bordes de todas las Cards de una vista: si la interfaz sigue funcionando, muchas de ellas nunca fueron necesarias. Cuando la repetición de tarjetas corresponda a una cuadrícula bento, aplica además la familia N.

---

### E. El espacio y la composición organizan, no decoran

**Núcleo:** El espacio en blanco, la simetría, las sombras y los radios de borde existen para organizar información y comunicar jerarquía real — no para simular sofisticación o modernidad.

**Justificación:** Aumentar artificialmente el espacio, alinear todo con simetría perfecta, o aplicar el mismo radio de borde a cada elemento sin excepción son recursos que se leen como "plantilla genérica" antes que como decisión de diseño.

| Patrón a evitar | Regla específica | Excepciones |
| :--- | :--- | :--- |
| Espacio en blanco aumentado solo para parecer más elegante | El espacio organiza información; no aumenta la sensación de modernidad por sí solo | — |
| Separación excesiva entre bloques o Cards para aparentar sofisticación | El espaciado responde al ritmo visual, no es un recurso decorativo | — |
| Composición perfectamente simétrica y centrada en todos los casos | La consistencia no implica simetría permanente; la composición varía cuando mejora la comunicación | Dashboards, tablas, interfaces altamente estructuradas, sistemas financieros, herramientas industriales |
| Sombra aplicada a cualquier bloque para diferenciarlo | La jerarquía se construye con composición, espaciado y tipografía; la sombra solo representa elevación o interacción real | — |
| Mismo radio de borde en absolutamente todos los elementos, sin relación con un sistema | El radio forma parte del lenguaje visual del sistema, no es un comportamiento automático | Design System existente, requisitos de marca, solicitud explícita del usuario |

**Verificación:** Si al eliminar una sombra, un espacio extra o un radio de borde la interfaz comunica exactamente igual, el recurso era decorativo.

---

### F. La tipografía comunica jerarquía real, no una firma visual de IA

**Núcleo:** La función de la tipografía es facilitar la comprensión de la estructura semántica del contenido. Cualquier recurso tipográfico que priorice el impacto visual sobre la legibilidad es sospechoso por defecto y necesita justificación explícita.

**Justificación:** Esta es la familia con más patrones identificables de un solo vistazo: cursivas para dar dramatismo, una palabra en negrita por párrafo, títulos partidos en fragmentos verticales ("Construye" / "*Mejor*" / "Productos"), over-headlines dentro de pills — todos aparecen con tanta frecuencia en contenido generado por IA que funcionan como huella digital.

| Patrón a evitar | Regla específica | Excepciones |
| :--- | :--- | :--- |
| Cursiva para generar dramatismo o aparentar sofisticación | La cursiva se usa solo con razón editorial objetiva | Citas textuales, títulos de libros, nombres de publicaciones, palabras extranjeras, nomenclatura científica, convención tipográfica del proyecto |
| Títulos alternando texto normal e itálico solo para generar contraste ("Human" / "*Centered*" / "Design") | La jerarquía se construye con composición, no alternando estilos tipográficos | — |
| Exactamente una palabra destacada por párrafo (negrita, cursiva, color o tamaño) | El énfasis responde al contenido, no a un patrón repetitivo | — |
| El mismo fragmento en negrita, cursiva, color y subrayado a la vez | Cada nivel de énfasis usa un único mecanismo visual; no se acumulan recursos | — |
| Peso tipográfico incrementado para diferenciar elementos que pertenecen al mismo nivel jerárquico | La jerarquía tipográfica corresponde a la estructura semántica del contenido, no a la necesidad de romper monotonía | — |
| Jerarquías con demasiados niveles dentro del mismo bloque (over-headline, título, subtítulo, descripción, lista, nota, micro-nota, CTA) | Reducir niveles jerárquicos; cada nivel adicional incrementa la carga cognitiva | — |
| Antetítulo (over-headline) por defecto encima del título, sin aportar clasificación real | El over-headline se usa solo cuando clasifica realmente el contenido | Documentación técnica, publicaciones editoriales, sistemas donde aporte contexto real, solicitud del usuario |
| Antetítulo metido dentro de una pill o cápsula redondeada, en casi todas las landings | No introducir un contenedor solo para hacer más visible un antetítulo | — |
| Texto fragmentado en frases sueltas verticales ("Pensar. / Construir. / Aprender. / Crecer.") | La fragmentación se usa solo cuando forma parte del ritmo narrativo, no como recurso repetitivo | — |
| Párrafos de una o dos líneas para aumentar artificialmente el espacio en blanco | La longitud del párrafo responde al contenido, no a una estética predeterminada | — |
| Saltos de línea usados para dramatizar una frase | El salto de línea mejora la lectura; no es un efecto visual | — |
| Títulos cortos y efectistas tipo eslogan de red social ("Think Bigger", "Build Faster") | El título comunica; no basta con que "suene bien" | — |
| Uso indiscriminado de MAYÚSCULAS para aparentar autoridad | Las mayúsculas responden al sistema tipográfico del proyecto | — |
| Tamaños, pesos, interlineado, espaciado o alineación modificados solo para que un bloque "se vea diferente" | Estos parámetros siguen un sistema coherente en toda la interfaz | — |

**Verificación:** Eliminar el recurso tipográfico en cuestión (cursiva, fragmentación, salto de línea dramático). Si el mensaje sigue comunicando igual de bien, el recurso no era necesario. Cuando el recurso tipográfico corresponda a una firma reconocible (tipografía monospaced para identificadores, fuente display pesada), aplica además la familia N.

---

### G. Se diseña para el uso real, no para la captura de pantalla

**Núcleo:** Una interfaz se evalúa por cómo funciona durante el uso, no por qué tan bien se ve en una imagen estática. El movimiento, los carruseles y las secciones adicionales se justifican solo cuando responden a información real o a un momento natural del recorrido del usuario.

**Justificación:** Diseñar pensando en la captura de pantalla lleva a acumular secciones, animaciones y movimiento continuo cuya única función es parecer una interfaz "premium", no comunicar mejor ni ser más usable.

| Patrón a evitar | Regla específica | Excepciones |
| :--- | :--- | :--- |
| Interfaz pensada para verse bien en una imagen, no para usarse | Se diseña para interacción real, no para obtener una captura atractiva | — |
| Cinta de texto desplazándose continuamente con palabras sueltas (Innovation, AI, Future, Cloud...) | El movimiento continuo responde a información dinámica real, no es decoración | — |
| Carrusel o slider aplicado incluso con muy pocos elementos | No introducir movimiento cuando una lista estática es más clara | — |
| Animación (fade, slide, zoom, scale, blur) aplicada por defecto a cada sección | Las animaciones comunican cambios reales, no decoran transiciones | — |
| CTA repetido al final de casi cada sección | Cada CTA responde a un momento natural del recorrido; no interrumpe continuamente la lectura | — |
| FAQ añadida por defecto sin dudas reales que resolver | La FAQ existe solo si hay dudas recurrentes reales, contenido complejo o soporte documental que la justifique | — |
| Secciones completas cuya única función es alargar la página | Toda sección responde a por qué existe, qué comunica y qué pasa si desaparece; si ninguna respuesta convence, se elimina | — |

**Verificación:** Para cada sección: si se elimina, ¿se rompe realmente la comunicación de la página? Si la respuesta es no, la sección se agregó por costumbre, no por necesidad.

### H. Estados de interfaz y microfeedback

**Núcleo:** Vacío, carga, error, deshabilitado e interacción (hover/active) son estados de diseño, no casos secundarios que se resuelven con un mensaje genérico o una transformación automática. El documento original no cubría este punto pese a ser una de las zonas donde más se nota una interfaz genérica.

**Justificación:** Los LLM aplican sistemáticamente `hover:scale-105` o cambios de color planos a cualquier elemento interactivo sin distinguir la naturaleza del componente. Un botón, un enlace y una tarjeta clicable deben responder de forma distinta porque su función es distinta.

| Patrón a evitar | Regla específica | Prioridad |
| :--- | :--- | :--- |
| Mensaje de error genérico ("Algo salió mal") sin indicar qué pasó ni qué hacer | El mensaje de error indica qué ocurrió y qué acción concreta puede tomar el usuario | ALTA |
| Estado vacío que solo dice "No hay datos" | El estado vacío explica por qué está vacío y, si aplica, ofrece la acción para llenarlo | ALTA |
| Spinner genérico para cualquier tiempo de espera, sin indicar progreso ni contexto | El estado de carga comunica qué se está procesando cuando la espera es significativa | ALTA |
| Elemento deshabilitado sin explicación de por qué lo está | El estado deshabilitado comunica la condición que falta para habilitarlo, cuando es razonable hacerlo | ALTA |
| Hover/active reducido a un cambio genérico de escala o color aplicado a todo elemento interactivo sin distinción | La respuesta visual al hover/active corresponde al tipo de elemento (botón, enlace, tarjeta, campo) y a su función. Un botón cambia de fondo; un enlace subraya; una tarjeta eleva ligeramente o muestra un borde; no se aplica el mismo `scale` o `brightness` a todos | ALTA |

**Verificación:** Para hover/active: si el mismo efecto (ej. `scale-105`) se aplica a botones, enlaces, tarjetas e inputs, la regla se ha violado. Cada elemento debe tener una respuesta visual distinta y predecible según su naturaleza.

### I. Accesibilidad real

**Núcleo:** El documento original mencionaba la accesibilidad únicamente como una de las condiciones que permite romper otra regla, sin definir un estándar propio. Esta familia lo convierte en requisito verificable, no en excepción.

| Patrón a evitar | Regla específica | Prioridad |
| :--- | :--- | :--- |
| Contraste de color insuficiente entre texto y fondo | El contraste cumple como mínimo el nivel AA de WCAG para texto normal | CRÍTICA |
| Estado de foco invisible o eliminado por estética | Todo elemento interactivo mantiene un indicador de foco visible para navegación por teclado | CRÍTICA |
| Información transmitida solo por color (por ejemplo, rojo/verde sin texto ni ícono) | Todo estado o dato relevante se comunica con al menos un canal adicional al color | CRÍTICA |
| Imágenes decorativas o informativas sin texto alternativo | Toda imagen con valor informativo tiene texto alternativo; las puramente decorativas se marcan como tales | CRÍTICA |

---

### J. Diseño responsive y adaptabilidad

**Núcleo:** El original no trataba el comportamiento de una interfaz fuera del viewport de escritorio. Reescalar proporcionalmente no es lo mismo que adaptar el contenido.

| Patrón a evitar | Regla específica | Prioridad |
| :--- | :--- | :--- |
| La misma jerarquía y densidad de información en móvil que en escritorio, solo reescalada | El breakpoint se decide por el contenido que deja de comunicarse bien, no por un ancho de pantalla arbitrario | ALTA |
| Tablas o grids complejos comprimidos sin reestructurar en pantallas pequeñas | El contenido tabular denso se reestructura (no solo se encoge) por debajo de un ancho razonable | ALTA |

---

### K. Movimiento reducido

**Núcleo:** El original prohíbe la animación automática por estética (familia G) pero no considera que, incluso cuando la animación está justificada, algunos usuarios necesitan poder desactivarla.

| Patrón a evitar | Regla específica | Prioridad |
| :--- | :--- | :--- |
| Animaciones que ignoran la preferencia de movimiento reducido del sistema | Toda animación no esencial respeta `prefers-reduced-motion` u equivalente | ALTA |

---

### L. Coherencia de color e iconografía

**Núcleo:** El original define coherencia tipográfica (familia F) pero no tiene equivalente para color o iconos, pese a que una paleta arbitraria por sección o iconos mezclados de librerías distintas es otra firma reconocible de interfaz genérica.

| Patrón a evitar | Regla específica | Prioridad |
| :--- | :--- | :--- |
| Paleta de color elegida sección por sección, sin sistema de tokens | El color sigue un sistema definido a nivel de proyecto, no una elección puntual por bloque | MEDIA |
| Iconos de librerías o estilos visuales distintos mezclados en la misma interfaz (algunos outline, otros filled, distinto grosor de trazo) | Todos los iconos de una misma interfaz comparten librería y estilo visual | MEDIA |

---

### M. Formularios

**Núcleo:** El original no trata formularios, una de las zonas donde una interfaz genérica se nota más rápido: validación ausente o genérica, placeholder usado como única guía.

| Patrón a evitar | Regla específica | Prioridad |
| :--- | :--- | :--- |
| Placeholder como único indicador de qué va en el campo (sin label visible) | Todo campo tiene un label visible; el placeholder es un ejemplo adicional, no un sustituto | ALTA |
| Mensaje de validación genérico ("Campo inválido") | El mensaje de error indica exactamente qué corregir | ALTA |
| Validación que solo aparece al enviar el formulario completo | La validación se comunica en el momento en que el usuario puede corregirla, cuando el contexto lo permite | ALTA |

---

### N. Estéticas y firmas visuales reconocibles de IA

**Núcleo:** Existen combinaciones visuales que se identifican de inmediato como "hechas con IA" porque proceden de estéticas popularizadas por aplicaciones y librerías concretas (Linear.app, v0.dev, Shadcn UI, Vercel, GitHub Actions) y heredadas masivamente por los modelos. Usar una de estas firmas por defecto no es una decisión de diseño: es un reflejo del entrenamiento. Cuando la interfaz corresponda a una firma reconocible, la elección se justifica por el proyecto, no por familiaridad.

**Justificación:** Los generadores de UI y los LLM se entrenan con las mismas librerías y ejemplos (Tailwind, Shadcn, paleta Zinc/Slate, Inter/Geist, badges de estado) y convergen al mismo aspecto; esa convergencia es lo que hace que una interfaz se reconozca como generada por IA. Esta familia cataloga las firmas más recurrentes para que el agente las detecte por nombre, las justifique o las elimine.

Las filas de esta familia son **CRÍTICA**: usarlas sin justificación explícita viola la regla. Heredan las Excepciones generales del capítulo.

| Patrón a evitar | Regla específica | Excepciones |
| :--- | :--- | :--- |
| Estética "Linear": tarjeta hero oscura incrustada sobre lienzo claro, bordes sutiles en gris claro, tonos charcoal/negro profundos con un único acento de color de alto contraste | La combinación se replica solo si responde al lenguaje gráfico del proyecto; no es el aspecto por defecto de una aplicación SaaS | Design System del proyecto, requisitos de marca, solicitud explícita del usuario |
| Estética "DevTools / Developer-First": tipografía híbrida (sans-serif para el texto principal + monospaced para identificadores como OP-001, etiquetas o versiones) y pills "terminal" (fondo verde oscuro, texto verde neón, punto o check) que imitan la salida de un terminal o la luz de estado de un servidor | La tipografía monospaced se limita a datos técnicos reales; los indicadores tipo terminal se usan solo cuando el dominio los justifica (CLIs, dashboards de infraestructura, documentación técnica), no como recurso para aparentar tecnicismo | Herramientas para desarrolladores, paneles de CI, documentación técnica, solicitud explícita del usuario |
| Bento Grid: bloques independientes de esquinas muy redondeadas montados en una cuadrícula simétrica para agrupar métricas o características | La cuadrícula bento se usa solo cuando los bloques tienen relación conceptual real; no es el layout por defecto para presentar métricas | Dashboards, paneles, galerías, catálogos, solicitud explícita del usuario |
| Estética "v0" / Shadcn UI: paleta Zinc o Slate, tarjetas flotantes con bordes finos, botones oscuros redondeados y tipografía Inter o Geist — sello distintivo de los generadores de UI por IA (v0.dev, Lovable, Bolt.new) | La apariencia se construye con los tokens y componentes del proyecto; el aspecto de librería por defecto no sustituye a un sistema de diseño | Proyecto que ya adopta ese Design System deliberadamente |
| Status / Pill Badge estilo CI/CD: punto circular brillante (a veces con pulso) o icono de check a la izquierda, texto corto técnico (v4.3 Adoptado, Deploying, Ready), borde de 1px de baja opacidad y relleno con tinte alpha del 10–20% (Soft/Subtle Badge) — origen en GitHub Actions y Vercel | El badge comunica un estado real; no se añade la parafernalia de pipeline (punto pulsante, tinte, contorno) cuando la jerarquía no lo requiere | Paneles de despliegue y CI, monitores, dashboards de infraestructura |
| Tipografía Brutalist Display / Neo-Grotesque Extruded: fuentes pesadas (heavy/black) con x-height muy alta y trazos geométricos inusuales (Syne, Clash Display, Cabinet Grotesk, Monument Extended) | Una fuente display pesada se adopta solo por identidad de marca o editorial verificable; el impacto visual no la justifica por sí solo | Branding, publicaciones editoriales, solicitud explícita del usuario |
| Editorial Bento / Neo-Brutalism Minimal: titular titánico que rompe la retícula, metadata en mayúsculas con letter-spacing amplio ("2025 • PHOTOGRAPHY") y tarjetas ultralimpias debajo — imita revistas de moda o galerías de arte | El contraste extremo de escalas se usa solo cuando la editorial o la marca lo exige; no es el recurso de impacto visual por defecto | Editoriales, portafolios, galerías, identidades de marca |

**Verificación:** Nombra la estética que estás usando. Si corresponde a una de estas firmas o a un clon reconocible (Linear, DevTools/terminal, bento, v0/Shadcn, badge CI/CD, brutalist display, editorial), ¿la elegiste por el proyecto o la heredaste del entrenamiento? Si no puedes justificarla con una intención funcional, editorial o de marca, cámbiala.

## Principio del capítulo

La calidad visual de una interfaz no depende del número de componentes utilizados, sino de la claridad con la que cada componente justifica su existencia. Eliminar un elemento innecesario mejora un diseño con más frecuencia que añadir uno nuevo.
