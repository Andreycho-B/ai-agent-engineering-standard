# 18. BASE DE DATOS

**Versión:** 2.0 (RFC-2026-004)
**Estado:** Normativo  
**Jerarquía:** Nivel 3 (Especializaciones)

---

## Propósito

La base de datos es la fuente persistente de información del sistema. Toda modificación debe preservar integridad, consistencia, trazabilidad, rendimiento y mantenibilidad. El agente no diseña una nueva base de datos en cada tarea; comprende el modelo existente antes de proponer cambios.

Este documento se integra con el **Protocolo Operativo (01)** (donde se ejecutan las intervenciones), la **Conciencia del Proyecto (09)** (para comprender el modelo existente y reutilizar), la **IA Generativa (13)** (para evitar sesgos), la **Arquitectura (17)** (para decisiones estructurales), el **Backend (16)** (para la integración con servicios), las **APIs (19)** (para contratos de datos), la **Seguridad (20)** (para proteger los datos), los **Principios de Ingeniería Avanzada (23)** (para aplicar el modelo de datos correcto), el **Testing Estratégico (22)** (para validar consultas), la **Observabilidad (21)** (para monitorear el rendimiento de la BD) y la **Memoria del Proyecto (24)** (para registrar decisiones de modelado y migraciones).

## DB-001 — Comprender el modelo y no crear por anticipación

**Prioridad:** CRÍTICA

**Regla:** Antes de modificar cualquier tabla, responde: ¿qué representa esta entidad? ¿qué relaciones posee? ¿qué restricciones existen? ¿qué procesos dependen de ella? ¿existe documentación del modelo? No modifiques una estructura sin comprender completamente su función. Cada nueva tabla debe responder a un requisito actual y verificable; nunca crees estructuras para escenarios hipotéticos.

**Verificación:** ¿Puedes explicar el propósito de cada tabla que modificas sin consultar el código? Si no, no la modifiques. ¿La nueva tabla responde a un requisito actual o a una suposición futura? Si es futura, no la crees.

---

## DB-002 — No duplicar entidades (referencia a PAP-002)

**Prioridad:** CRÍTICA

**Regla:** Aplica el principio definido en **PAP-002** (Conciencia del Proyecto) al contexto específico de entidades, tablas y modelos de datos. Antes de crear una tabla nueva, busca si el dominio ya posee una entidad equivalente. Prefiere extender una entidad existente antes que duplicarla. Cada dato debe tener un único lugar oficial de almacenamiento. Evita almacenar la misma información en múltiples tablas salvo que exista una justificación técnica claramente documentada. La desnormalización solo se realiza cuando exista evidencia objetiva de que la normalización resulta insuficiente. No almacenes datos derivados que puedan calcularse directamente a partir de otros datos, salvo beneficio objetivo demostrado.

**Verificación:** ¿Existe ya una entidad que represente el mismo concepto? Si es así, extiéndela. ¿El mismo dato aparece en múltiples tablas sin justificación? Si es así, consolida. ¿Estás almacenando un valor calculable? Si no hay beneficio de rendimiento, elimínalo.

**Dependencias:** PAP-002

## DB-003 — Preservar integridad referencial y restricciones

**Prioridad:** CRÍTICA

**Regla:** Toda relación entre entidades debe mantenerse mediante mecanismos explícitos de integridad (claves foráneas). No dependas únicamente de la lógica de la aplicación para preservar relaciones críticas. No elimines claves foráneas, restricciones UNIQUE, CHECK, NOT NULL o índices críticos sin una justificación objetiva respaldada por el dominio. La elección del identificador (clave natural vs. artificial) debe responder a las necesidades del dominio, no a un patrón único para todos los casos. Toda columna debe expresar explícitamente el dato que representa; evita nombres genéricos como `data`, `info`, `value`, `extra`, `misc`, `field1`, `json_data`.

**Verificación:** ¿Todas las relaciones críticas tienen claves foráneas explícitas? Si no, añádelas. ¿Hay restricciones eliminadas sin justificación? Si es así, revísalas. ¿Hay columnas con nombres genéricos? Si es así, renómbralas según el dominio.

## DB-004 — Consultas SQL eficientes

**Prioridad:** CRÍTICA

**Regla:** Selecciona únicamente las columnas necesarias; nunca uses `SELECT *` salvo durante exploración o depuración temporal. Analiza el número real de consultas ejecutadas; consolida consultas cuando sea apropiado. No ejecutes consultas repetitivas dentro de bucles; resuélvelas con una única consulta. Toda operación de filtrado debe realizarse lo más cerca posible de la fuente de datos, no en memoria después de recuperar todos los registros. No uses `DISTINCT` para ocultar duplicados; resuelve el origen del problema. Evalúa si un JOIN, EXISTS o una reestructuración es más simple y eficiente que una subconsulta. Ordena solo cuando el consumidor realmente lo necesite. La paginación debe realizarse en la base de datos, no recuperando todos los registros para paginar en memoria.

**Verificación:** Revisa el SQL generado: ¿usas `SELECT *`? Si es así, cámbialo por columnas explícitas. ¿Hay consultas dentro de bucles? Si es así, consolídalas. ¿Estás filtrando en memoria? Si es así, mueve el filtro a la base de datos. ¿Usas `DISTINCT`? Si es así, verifica si es necesario o encubre un problema.

## DB-005 — ORM: SQL consciente, Lazy y Eager Loading controlados

**Prioridad:** CRÍTICA

**Regla:** Comprende siempre el SQL generado por el ORM. El ORM es una herramienta, no reemplaza el conocimiento del modelo relacional. Toda carga diferida (Lazy Loading) debe ser consciente y justificada; evita consultas ocultas durante la navegación de objetos. No abuses del Eager Loading: no cargues relaciones completas cuando solo necesitas pocos datos. No crees modelos ORM que solo envuelven otra entidad sin aportar comportamiento. Antes de asumir que una consulta es eficiente, verifica: SQL generado, número de consultas, índices utilizados y plan de ejecución.

**Verificación:** ¿Sabes qué SQL genera cada operación del ORM? Si no, actívalo y revísalo. ¿Hay Lazy Loading causando consultas adicionales inesperadas? Si es así, haz explícito lo que se carga. ¿Estás cargando relaciones innecesarias? Si es así, reduce el Eager Loading.

## DB-006 — Índices basados en consultas reales

**Prioridad:** ALTA

**Regla:** Todo índice debe existir porque acelera consultas reales, no por intuición. Antes de crear un índice, comprueba si otro existente ya cubre el mismo patrón. No crees índices sobre todas las columnas; cada índice añade coste de escritura y debe justificarse. Los índices deben revisarse periódicamente; elimina aquellos cuya inutilidad pueda demostrarse.

**Verificación:** ¿Cada índice está respaldado por una consulta real y medidas de rendimiento? Si no, elimínalo. ¿Hay índices duplicados o redundantes? Si es así, consolida. ¿Has verificado que los índices se utilizan realmente (EXPLAIN)? Si no, hazlo.

## DB-007 — Migraciones deterministas y no destructivas

**Prioridad:** CRÍTICA

**Regla:** Toda migración debe producir exactamente el mismo resultado independientemente del entorno. Considera datos incompletos, inconsistentes o históricos en cada migración; no asumas datos limpios. Evita mezclar modificaciones del esquema con transformaciones masivas de datos cuando puedan ejecutarse por separado. No elimines columnas o tablas inmediatamente después de dejar de utilizarlas; respeta periodos de transición cuando el proyecto lo requiera.

**Verificación:** ¿La migración funciona en todos los entornos (desarrollo, staging, producción)? Si no, revísala. ¿Eliminas datos sin un plan de transición? Si es así, añade un periodo de deprecación.

---

## DB-008 — Transacciones pequeñas y sin operaciones lentas

**Prioridad:** CRÍTICA

**Regla:** Las transacciones deben abarcar solo las operaciones que realmente deban ejecutarse de forma atómica. Abre la transacción en el último momento posible y ciérrala en el primero posible. No realices llamadas HTTP, operaciones de archivos, procesamiento pesado o esperas mientras una transacción permanece abierta.

**Verificación:** ¿La transacción abarca solo lo necesario? ¿Hay operaciones lentas dentro de la transacción? Si es así, sácalas fuera. ¿La transacción se abre demasiado pronto o se cierra demasiado tarde? Si es así, ajusta los límites.

---

## DB-009 — Rendimiento: medir antes de optimizar

**Prioridad:** CRÍTICA

**Regla:** Toda optimización debe apoyarse en métricas, no en intuiciones. Las consultas críticas deben validarse mediante EXPLAIN o la herramienta equivalente del motor utilizado. Recupera únicamente las columnas, filas y relaciones necesarias. Toda transferencia innecesaria constituye deuda de rendimiento.

**Verificación:** ¿Has medido el rendimiento antes de optimizar? Si no, hazlo. ¿Has validado el plan de ejecución de las consultas críticas? Si no, hazlo. ¿Estás recuperando datos que no necesitas? Si es así, recorta la consulta.

---

## DB-010 — Evitar Database IA Slop y preservar identidad

**Prioridad:** CRÍTICA

**Regla:** Detecta y elimina indicadores de base de datos generada por IA: tablas duplicadas, columnas genéricas, restricciones eliminadas por costumbre, índices creados sin justificación, migraciones no deterministas, transacciones innecesariamente largas, consultas ineficientes (`SELECT *`, N+1, filtros en memoria), uso ciego del ORM sin comprender el SQL generado, y falta de integridad referencial.

Después de cualquier modificación, el esquema debe seguir pareciendo diseñado por el mismo equipo; no introduzcas convenciones, nomenclaturas o estilos incompatibles con el resto del proyecto. Toda modificación debe estar respaldada por una necesidad objetiva, no por preferencias personales o modas.

**Verificación:** Revisa el esquema modificado: ¿un desarrollador del equipo podría identificar qué partes escribiste por diferencias de estilo? Si es así, adáptate a las convenciones existentes. ¿Cada cambio está justificado por una necesidad real? Si no, revísalo. ¿Hay algún indicador de IA Slop (nombres genéricos, falta de integridad, consultas ineficientes)? Si es así, corrígelo.

## DB-011 — Prohibición de ORMs pesados con generación implícita de consultas en rutas críticas

**Prioridad:** CRÍTICA

**Regla:** Queda **TERMINANTEMENTE PROHIBIDO** el uso de ORMs complejos con generación implícita de SQL, relaciones mágicas o carga perezosa (*lazy loading*) como Prisma o GORM en las rutas de ejecución de negocio críticas. El acceso a datos **DEBERÁ** ser transparente, predecible y optimizado directamente sobre el motor de base de datos.

**Justificación:** Los ORMs pesados inducen a los modelos de lenguaje a generar consultas ineficientes ($N+1$), acoplan el esquema relacional a modelos de memoria frágiles y causan arranques en frío lentos en arquitecturas de contenedores o edge.

**Verificación:** ¿El proyecto prescinde de ORMs basados en carga diferida implícita en la lógica central?

## DB-012 — Consultas SQL tipadas en compilación obligatorias (sqlc y Drizzle)

**Prioridad:** CRÍTICA

**Regla:** El acceso a la base de datos relacional (PostgreSQL) **DEBERÁ** realizarse mediante herramientas que compilen y verifiquen el SQL en tiempo de construcción:
1. En servicios Go: Se utilizará obligatoriamente **`sqlc`** sobre el driver nativo **`pgx`**. Las consultas se redactan en SQL estándar y se compilan a funciones Go fuertemente tipadas.
2. En servicios TypeScript: Se utilizará obligatoriamente **`Drizzle ORM`** como constructor de consultas SQL tipadas de cero sobrecarga.

**Justificación:** `sqlc` y `Drizzle` garantizan que cualquier discrepancia entre el esquema de base de datos y el código de la aplicación se detecte en compilación, impidiendo errores en producción.

**Verificación:** ¿Todas las consultas SQL están verificadas contra el esquema mediante `sqlc` o `Drizzle` sin cadenas no tipadas?

## DB-013 — Aislamiento multi-inquilino estricto mediante esquemas dedicados o RLS nativo auditado

**Prioridad:** CRÍTICA

**Regla:** En arquitecturas de software multi-inquilino (*multi-tenant*), el aislamiento de datos entre organizaciones **DEBERÁ** garantizarse a nivel de motor de base de datos, ya sea mediante esquemas dedicados (`tenant_schema`) o mediante políticas de **Row Level Security (RLS)** nativas de PostgreSQL estrictamente auditadas. Queda **PROHIBIDO** confiar el aislamiento multi-inquilino únicamente a condiciones `WHERE tenant_id = ?` añadidas manualmente en la aplicación.

**Justificación:** El aislamiento a nivel de base de datos impide fugas de información entre inquilinos ante eventuales omisiones de filtros en el código del servidor.

**Verificación:** ¿La base de datos rechaza consultas que intenten acceder a datos de otro inquilino aun si la aplicación omite el filtro?

## DB-014 — Criterios de exclusión de EdgeDB (Gel) y uso condicional de BaaS (Supabase / Xata)

**Prioridad:** ALTA

**Regla:** 
1. **Descarte de EdgeDB (Gel):** Queda **DESACONSEJADO** el uso de EdgeDB como base de datos primaria en nuevos proyectos; el estándar mandata **PostgreSQL** estándar para garantizar portabilidad y herramientas universales.
2. **Backend-as-a-Service (Supabase / Xata):** Se autoriza el uso de **Supabase** o **Xata** exclusivamente para acelerar prototipos, gestión de usuarios con RLS y almacenamiento de archivos (*object storage*). Queda **PROHIBIDO** delegar transacciones críticas de alta contención (pedidos, pagos con bloqueo pesimista) a funciones serverless sin control transaccional en el núcleo de Go.

**Justificación:** Evitar el vendor lock-in en bases de datos propietarias y asegurar que las transacciones financieras y de pedidos mantengan garantías ACID completas en el servidor transaccional.

**Verificación:** ¿El sistema utiliza PostgreSQL estándar? Si se usa Supabase, ¿las operaciones transaccionales críticas están gobernadas por el backend de Go?

## Principio fundamental

La base de datos es la memoria persistente del sistema. Su integridad y rendimiento son responsabilidad crítica del agente. No se diseña para demostrar conocimiento, sino para preservar la coherencia de los datos, minimizar la complejidad y garantizar que cada cambio sea una evolución natural del modelo existente. Un esquema bien diseñado no es el más sofisticado, sino el que representa fielmente el dominio con la menor complejidad posible.
