# 19. APIs Y CONTRATOS

**Versión:** 2.0 (RFC-2026-004)
**Estado:** Normativo  
**Jerarquía:** Nivel 3 (Especializaciones)

---

## Propósito

Las APIs son el contrato de comunicación entre sistemas. Toda modificación debe preservar estabilidad, compatibilidad, claridad, seguridad y previsibilidad. El agente no rediseña una API durante tareas funcionales; comprende el contrato existente antes de introducir cambios y minimiza el impacto sobre los consumidores.

Este documento se integra con el **Protocolo Operativo (01)** (donde se ejecutan las intervenciones), la **Conciencia del Proyecto (09)** (para comprender el contrato existente y reutilizar), la **IA Generativa (13)** (para evitar sesgos), el **Backend (16)** (para la lógica de negocio), la **Arquitectura (17)** (para decisiones estructurales), la **Base de Datos (18)** (para la persistencia), la **Seguridad (20)** (para proteger los contratos), los **Principios de Ingeniería Avanzada (23)** (para aplicar versionado y diseño de contratos), el **Testing Estratégico (22)** (para validar contratos), la **Observabilidad (21)** (para monitorear el rendimiento de las APIs) y la **Memoria del Proyecto (24)** (para registrar decisiones de diseño de API).

## API-001 — Comprender y preservar el contrato

**Prioridad:** CRÍTICA

**Regla:** Antes de modificar cualquier endpoint, responde: ¿quién consume esta API? ¿qué contratos públicos existen? ¿qué versiones están activas? ¿qué clientes podrían romperse? ¿existen consumidores externos? Toda modificación debe intentar mantener compatibilidad hacia atrás. Los cambios incompatibles requieren justificación explícita. No modifiques nombres, rutas, parámetros, tipos, respuestas o códigos HTTP sin analizar todos los consumidores. Modificar el comportamiento de un endpoint sin alterar su contrato es un cambio igualmente importante y debe tratarse como tal.

**Verificación:** Si modificas un endpoint, ¿puedes garantizar que ningún consumidor existente se romperá? Si no, ¿has documentado el cambio y comunicado la deprecación? Si el cambio es incompatible, ¿está justificado por una necesidad objetiva?

## API-002 — No duplicar endpoints (referencia a PAP-002)

**Prioridad:** CRÍTICA

**Regla:** Aplica el principio definido en **PAP-002** (Conciencia del Proyecto) al contexto específico de endpoints y contratos de API. Antes de crear un nuevo endpoint, busca si ya existe uno equivalente que pueda ampliarse, parametrizarse o reutilizarse. No crees endpoints duplicados. Si dos endpoints resuelven el mismo problema con pequeñas variaciones, unifícalos o parametriza el existente.

**Verificación:** ¿Ya existe un endpoint que haga algo similar? ¿Puedes extenderlo en lugar de crear uno nuevo? Si no puedes justificar por qué el existente no sirve, no crees uno nuevo.

**Dependencias:** PAP-002

## API-003 — Consistencia, responsabilidad y estilo REST

**Prioridad:** ALTA

**Regla:** Cada endpoint debe representar una operación claramente definida. Evita endpoints multipropósito. La estructura de rutas, verbos HTTP y recursos debe seguir una convención uniforme dentro del proyecto. No mezcles estilos distintos. Si el proyecto usa REST, prefiere recursos antes que acciones en las rutas, pero respeta siempre la arquitectura existente.

**Verificación:** ¿El endpoint tiene una única responsabilidad? ¿Su ruta y verbo son consistentes con el resto de la API? Si no, alinealo con las convenciones del proyecto.

---

## API-004 — Respuestas mínimas y paginación

**Prioridad:** CRÍTICA

**Regla:** Toda respuesta debe contener únicamente la información requerida por el consumidor. No devuelvas colecciones masivas sin paginación o segmentación. Si una colección puede crecer, implementa paginación. Evita respuestas infladas que aumenten el coste de transferencia y procesamiento.

**Verificación:** ¿El consumidor necesita todos los campos que estás devolviendo? Si no, recorta la respuesta. Si la colección puede superar los 100 elementos, ¿has implementado paginación?

---

## API-005 — Coherencia de nombres, DTOs y estados explícitos

**Prioridad:** CRÍTICA

**Regla:** Los nombres de endpoints, parámetros, DTOs y propiedades deben seguir las convenciones del proyecto. Un mismo campo no debe representar conceptos distintos en diferentes contextos. Evita DTOs gigantes, duplicados, con propiedades nunca utilizadas, campos opcionales innecesarios, estructuras copiadas entre endpoints, o objetos profundamente anidados sin necesidad. Todo parámetro debe tener un significado único y documentable. No uses múltiples flags booleanos para representar una máquina de estados; utiliza un modelo explícito de estados.

**Verificación:** ¿Los nombres son consistentes con el resto del proyecto? ¿Cada campo tiene un significado claro y único? Si tienes más de tres flags booleanos que representan estados, reemplázalos por un enum o campo de estado.

---

## API-006 — Validación de toda entrada

**Prioridad:** CRÍTICA

**Regla:** Nunca confíes en datos provenientes del cliente. Toda entrada debe validarse. Cada validación debe ejecutarse en la capa responsable; no repitas la misma lógica en múltiples niveles. La validación en el controlador es mínima; la lógica de negocio valida lo que corresponde al dominio.

**Verificación:** ¿Todas las entradas están validadas? ¿Hay validaciones duplicadas en diferentes capas? Si es así, consolídalas en una única capa.

---

## API-007 — Manejo de errores y códigos HTTP

**Prioridad:** CRÍTICA

**Regla:** Toda respuesta de error debe ser consistente en estructura y contenido. No devuelvas siempre 200 OK. El código HTTP debe reflejar correctamente el resultado de la operación (2xx para éxito, 4xx para errores de cliente, 5xx para errores de servidor). No utilices excepciones para flujo normal de negocio; las excepciones son para condiciones excepcionales.

**Verificación:** ¿Los códigos HTTP son correctos según el resultado? ¿Los errores tienen una estructura consistente? ¿Estás usando excepciones para control de flujo? Si es así, reemplázalas por respuestas de error explícitas.

---

## API-008 — Lógica en capas y consultas eficientes

**Prioridad:** CRÍTICA

**Regla:** El controlador coordina; no implementa reglas de negocio. La lógica de negocio pertenece a la capa de servicios o dominio. Analiza el número real de consultas ejecutadas por cada endpoint. No realices consultas redundantes. Reduce dependencias y consolida operaciones cuando sea apropiado; evita llamadas en cascada innecesarias.

**Verificación:** ¿El controlador contiene lógica de negocio? Si es así, muévela a servicios. ¿Cuántas consultas ejecuta el endpoint? Si son más de las necesarias, optimiza.

---

## API-009 — Versionado y deprecación

**Prioridad:** CRÍTICA

**Regla:** El versionado es el último recurso. Antes de crear una nueva versión, evalúa mecanismos compatibles (campos opcionales, nuevos parámetros con defaults). Si una nueva versión es necesaria, la anterior debe pasar por un proceso de deprecación antes de su eliminación. Toda modificación importante del contrato debe documentarse. Los consumidores deben conocer qué cambió y por qué.

**Verificación:** ¿Has agotado todas las opciones compatibles antes de versionar? Si estás deprecando un endpoint, ¿has comunicado el plazo y la alternativa? Si no, hazlo.

---

## API-010 — Evitar API IA Slop y preservar identidad

**Prioridad:** CRÍTICA

**Regla:** Detecta y elimina indicadores de API generada por IA: endpoints duplicados, rutas inconsistentes, DTOs redundantes, respuestas gigantes, parámetros ambiguos, validaciones repetidas, códigos HTTP incorrectos, endpoints multipropósito, lógica de negocio en controladores, contratos incompatibles, versionado innecesario y documentación desactualizada.

Después de cualquier modificación, la API debe seguir pareciendo diseñada por el mismo equipo. No introduzcas convenciones, nomenclaturas o estilos incompatibles con el resto del proyecto. Toda modificación del contrato debe estar respaldada por una necesidad objetiva, no por preferencias personales o modas.

**Verificación:** Revisa tu API modificada: ¿un desarrollador del equipo podría identificar qué partes escribiste por diferencias de estilo? Si es así, adáptate a las convenciones existentes. ¿Cada cambio está justificado por una necesidad real? Si no, revísalo.

## API-011 — Contratos tipados inmutables entre servicios mediante Protobuf y ConnectRPC / gRPC

**Prioridad:** CRÍTICA

**Regla:** La comunicación entre frontend y backend en sistemas desacoplados (o entre servicios internos) **DEBERÁ** gobernarse mediante contratos formales e inmutables definidos en esquemas Protocol Buffers (`.proto`) utilizando **ConnectRPC** o **gRPC**. Las estructuras de datos y clientes en Go y TypeScript **DEBERÁN** autogenerarse a partir de estos esquemas. Para APIs REST públicas, se exigirá un contrato formal equivalente verificado mediante **OpenAPI 3.1 / JSON Schema**.

**Justificación:** Un contrato formal inmutable elimina la ambigüedad y la desincronización de tipos entre equipos o capas, garantizando que el agente de IA nunca invente propiedades en los payloads.

**Verificación:** ¿Los contratos de API están respaldados por esquemas `.proto` o JSON Schema verificables en compilación?

## API-012 — Arquitectura de tiempo real desacoplada con broker pub/sub interno (NATS.io) y motor de clientes (Centrifugo)

**Prioridad:** ALTA

**Regla:** Las capacidades de actualización en tiempo real (pedidos en vivo, notificaciones de fidelización, chat) **DEBERÁN** desacoplarse del servicio transaccional principal:
1. **Broker interno:** Se adoptará **NATS.io** como bus de eventos pub/sub de alta velocidad en Go.
2. **Motor hacia el navegador:** Se adoptará **Centrifugo** para gestionar las conexiones persistentes masivas (WebSockets / SSE) hacia los clientes, consumiendo eventos emitidos por NATS.

Queda **PROHIBIDO** mantener conexiones WebSocket masivas directamente en el proceso principal de lógica de negocio o base de datos.

**Justificación:** Desacoplar la gestión de conexiones de socket protege al núcleo transaccional de la saturación de descriptores de archivos y degradación de memoria.

**Verificación:** ¿La gestión de WebSockets masivos está delegada a un broker especializado sin bloquear la API central?

## API-013 — Ámbito de aplicación de tRPC frente a ConnectRPC / Protobuf

**Prioridad:** MEDIA

**Regla:** 
1. **tRPC:** Se autoriza el uso de **tRPC** única y exclusivamente cuando el frontend y el backend compartan el mismo monorepositorio TypeScript de principio a fin.
2. **ConnectRPC / Protobuf:** Cuando el backend esté implementado en Go (o Rust) y el frontend en TypeScript, el contrato cliente-servidor **DEBERÁ** definirse obligatoriamente mediante esquemas Protocol Buffers (`.proto`) utilizando **ConnectRPC**.

**Justificación:** tRPC no puede traspasar la frontera entre lenguajes; ConnectRPC garantiza tipado estricto cruzado entre Go y TypeScript con cero código duplicado.

**Verificación:** ¿Se utiliza ConnectRPC para la frontera Go/TS y tRPC solo en arquitecturas monolíticas TS puras?

## Principio fundamental

Una API es un contrato que vincula a productores y consumidores. La responsabilidad del agente no es diseñar la API más elegante, sino preservar su estabilidad, claridad y compatibilidad, minimizando el impacto sobre los consumidores y evitando cambios estructurales innecesarios. La confianza en una API se construye con estabilidad; se destruye con cambios arbitrarios.
