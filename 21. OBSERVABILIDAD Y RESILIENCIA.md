# 21. OBSERVABILIDAD Y RESILIENCIA

**Versión:** 1.1  
**Estado:** Normativo  
**Jerarquía:** Nivel 3 (Especializaciones)

---

## Propósito

Define los estándares mínimos para que el sistema sea **observable** (capaz de revelar su estado interno a través de logs, métricas y trazas) y **resiliente** (capaz de manejar fallos externos e internos sin colapsar). Un sistema que funciona en desarrollo pero falla en producción sin dejar rastro es un sistema que no se puede mantener. La observabilidad y la resiliencia son requisitos de producción, no características opcionales.

Este documento se integra con el **Protocolo Operativo (01)** (donde se ejecutan las intervenciones), la **Conciencia del Proyecto (09)** (para comprender el contexto), la **IA Generativa (13)** (para evitar sesgos), el **Backend (16)** , la **Arquitectura (17)** , la **Base de Datos (18)** , las **APIs (19)** y el **Frontend (15)** (donde se implementa la observabilidad), los **Principios de Ingeniería Avanzada (23)** (para aplicar estrategias de resiliencia como circuit breakers y bulkheads), el **Testing Estratégico (22)** (para validar la observabilidad y resiliencia) y la **Memoria del Proyecto (24)** (para registrar incidentes y decisiones de resiliencia).

## OBS-001 — Logs estructurados y niveles

**Prioridad:** CRÍTICA

**Regla:** Todo log debe ser **estructurado** (formato JSON) para permitir búsqueda y agregación automática. Prohibido usar logs en texto plano con formato libre.

Los logs DEBEN incluir al menos:
- `timestamp` (ISO 8601 con zona horaria UTC).
- `level` (ERROR, WARN, INFO, DEBUG).
- `message` (mensaje legible para humanos, pero conciso).
- `trace_id` (correlación entre servicios, ver OBS-002).
- `component` (servicio, módulo, o clase que genera el log).
- `user_id` o `session_id` si está disponible (para trazabilidad de acciones de usuario).

**Regla de niveles:**
- **ERROR:** Fallos que requieren intervención humana o afectan al negocio (ej: BD caída, pago rechazado).
- **WARN:** Comportamientos inesperados pero recuperables (ej: reintento exitoso, timeout superado pero con fallback).
- **INFO:** Eventos importantes del ciclo de vida (ej: inicio/fin de servicio, creación de un pedido, inicio de sesión).
- **DEBUG:** Solo para entornos de desarrollo o bajo petición expresa. Prohibido en producción.

**Regla de seguridad:** Está prohibido registrar credenciales, tokens, contraseñas o información personal identificable (PII). Si un log contiene datos sensibles, debe ser enmascarado (ej: `email: "us***@ejemplo.com"`).

**Verificación:** Revisa los logs generados por tu código. ¿Están en JSON? ¿Tienen los campos mínimos requeridos? ¿Hay información sensible expuesta? Si falta algún campo o hay datos sensibles, corrígelo.

## OBS-002 — Correlation ID / Trace ID (Trazabilidad Distribuida)

**Prioridad:** CRÍTICA

**Regla:** Toda petición que entre al sistema (HTTP, cola, evento) DEBE generar o recibir un `trace_id` único que se propague a través de todas las llamadas internas (servicios, colas, logs, y respuestas al cliente). Este identificador permite rastrear el recorrido completo de una transacción.

**Regla de implementación:**
- Si el cliente envía un `X-Request-ID`, el agente DEBE usarlo como `trace_id`.
- Si no existe, el agente DEBE generar uno nuevo (UUID v4 o similar).
- El `trace_id` DEBE incluirse en los headers de todas las llamadas HTTP salientes.
- El `trace_id` DEBE registrarse en cada log asociado a esa petición.

**Verificación:** Elige una petición cualquiera en el sistema. ¿Puedes rastrear su recorrido completo (entrada → servicio → BD → respuesta) usando solo el `trace_id`? Si no, falta propagación.

## OBS-003 — Health Checks: Liveness y Readiness

**Prioridad:** CRÍTICA

**Regla:** Todo servicio DEBE exponer dos endpoints de salud separados, con semántica específica para orquestadores (Kubernetes, ECS, etc.):

- **`/health/liveness`**: Indica si el proceso sigue vivo y puede recibir peticiones. Si falla, el orquestador reinicia el contenedor. Debe ser simple y rápido (ej: comprobar que el servidor responde). NO debe verificar dependencias externas.
- **`/health/readiness`**: Indica si el servicio está listo para recibir tráfico (ej: conexión a BD, cache cargada). Si falla, el orquestador retira el servicio del balanceador de carga (no recibe tráfico). DEBE verificar dependencias críticas (BD, colas, API externas).

**Regla de diseño:** Los health checks deben responder en < 100 ms y no deben tener efectos secundarios (ej: modificar datos). El endpoint de readiness puede tener un timeout más largo (ej: 500 ms).

**Verificación:** Si has desplegado un servicio sin estos endpoints, estás violando la regla. Si `liveness` depende de la BD y la BD cae, tu servicio se reiniciará en bucle (mal diseño). Verifica que cada endpoint tenga la responsabilidad correcta.

## OBS-004 — Timeouts obligatorios (Conexión y Lectura)

**Prioridad:** CRÍTICA

**Regla:** Toda operación que implique una red (HTTP, TCP, base de datos, colas) DEBE tener configurados timeouts explícitos. Nunca confíes en los timeouts por defecto del sistema operativo o del framework, que suelen ser demasiado largos (ej: 30s, 60s, o infinito).

**Valores orientativos (ajustar según dominio):**
- **Connection timeout:** ≤ 1 segundo (fallar rápido si el destino no responde).
- **Request/Read timeout:** ≤ 3 segundos para APIs internas; ≤ 5 segundos para APIs externas; ≤ 30 segundos para procesos batch (ajustable).
- **Database timeout:** ≤ 2 segundos para consultas simples; ≤ 10 segundos para reportes pesados (justificado).

**Verificación:** Revisa todas las llamadas externas en tu código. ¿Tienen un timeout configurado explícitamente? Si ves `await fetch(url)` sin `timeout` o `setTimeout`, estás en falta. Configúralos.

## OBS-005 — Retries con Backoff y Jitter

**Prioridad:** ALTA

**Regla:** Cuando una llamada externa falla por un error transitorio (timeout, 5xx, conexión rechazada), el agente DEBE implementar un reintento con **exponential backoff + jitter**. No reintentes inmediatamente ni indefinidamente.

**Mecanismo recomendado:**
- Número de reintentos: ≤ 3 (para operaciones idempotentes).
- Espera inicial: 100 ms.
- Factor de backoff: 2 (100ms → 200ms → 400ms).
- **Jitter:** Añadir aleatoriedad a la espera (±20%) para evitar "thundering herd" (todos los servicios reintentando a la vez).
- **Límite máximo de espera:** 5 segundos.

**Excepciones:** No reintentar peticiones no idempotentes (ej: POST de creación de recurso) a menos que se pueda garantizar la idempotencia (ej: usando `Idempotency-Key`).

**Verificación:** Si haces reintentos manuales (`while retries < 3 { try { ... } catch { wait(1s) } }`) sin backoff ni jitter, estás generando un riesgo de tormenta de reintentos. Corrígelo.

## OBS-006 — Circuit Breakers y Fallbacks

**Prioridad:** ALTA

**Regla:** Cuando una dependencia externa falla repetidamente (ej: > 50% de errores en un minuto), el agente DEBE activar un **Circuit Breaker** (disyuntor) para evitar seguir llamándola y saturar el sistema.

**Estados del Circuit Breaker:**
1. **Cerrado:** Las peticiones pasan normalmente. Se cuentan los fallos.
2. **Abierto:** Las peticiones fallan inmediatamente sin llamar al destino (timeout rápido o error). Después de un tiempo (ej: 30s), pasa a medio-abierto.
3. **Medio-Abierto:** Se permite una petición de prueba. Si falla, vuelve a abierto. Si funciona, vuelve a cerrado.

**Fallback:** Cuando el circuito está abierto o la llamada falla, el agente DEBE proporcionar un valor por defecto o una respuesta alternativa (ej: "El servicio no está disponible, intente más tarde", o usar datos cacheados).

**Verificación:** Si una dependencia externa se cae, ¿tu servicio deja de responder o responde con un mensaje controlado y un fallback? Si tu servicio se cuelga o lanza una excepción no manejada, necesitas un Circuit Breaker.

## OBS-007 — Rate Limiting y Bulkheads (Protección de recursos)

**Prioridad:** MEDIA

**Regla:** El agente DEBE proteger los recursos internos (conexiones a BD, threads, memoria) de un pico de tráfico.

- **Rate Limiting:** Limitar el número de peticiones por usuario / IP / servicio por segundo (ej: 100 req/seg). Protege la capa de presentación.
- **Bulkheads (Compartimentos):** Aislar el pool de conexiones a BD para que un módulo con alta demanda no agote las conexiones de otro módulo. Ejemplo: configurar pools separados para lecturas y escrituras, o para microservicios distintos.

**Regla de aplicación:** Si el sistema tiene picos de tráfico predecibles (ej: hora punta) o depende de recursos limitados (ej: número de conexiones a BD), el agente DEBE implementar estas estrategias. Si el sistema es pequeño (< 100 req/seg), puede omitirlo, pero debe documentar la decisión.

**Verificación:** Si una consulta pesada a BD deja al resto del sistema sin conexiones (timeout de pool), tu sistema no tiene bulkheads. Implementa separación de pools.

## OBS-008 — Graceful Shutdown (Finalización controlada)

**Prioridad:** CRÍTICA

**Regla:** El servicio DEBE capturar señales del sistema (`SIGTERM`, `SIGINT`) para iniciar un apagado controlado antes de terminar el proceso. Esto incluye:

1. **Dejar de aceptar nuevas conexiones** (desactivar el puerto o responder con 503).
2. **Esperar a que las peticiones en curso terminen** (con un timeout razonable, ej: 10 segundos).
3. **Cerrar conexiones activas** (BD, colas, HTTP client).
4. **Liberar recursos** y registrar la finalización.
5. **Finalizar el proceso** después de completar la limpieza.

**Regla de tiempo:** El tiempo total de graceful shutdown NO DEBE exceder los 30 segundos (límite típico en orquestadores). Si la limpieza requiere más tiempo, se debe considerar el uso de tareas asíncronas en background o ajustar la configuración del orquestador.

**Verificación:** ¿Tu servicio maneja `SIGTERM`? ¿Si matas el proceso (`kill -15`), termina limpiamente o se corta abruptamente? Si no maneja señales, está en falta.

## OBS-009 — Métricas RED y USE

**Prioridad:** ALTA

**Regla:** El agente DEBE exponer métricas clave para monitoreo proactivo (ej: Prometheus, OpenTelemetry). Se recomienda seguir el método **RED** (para servicios) y **USE** (para recursos):

**Método RED (para servicios):**
- **Rate:** Número de peticiones por segundo.
- **Errors:** Porcentaje de peticiones que fallan (5xx, timeouts).
- **Duration:** Distribución de latencias (P50, P95, P99).

**Método USE (para recursos - opcional):**
- **Utilization:** % de uso de CPU, memoria, disco.
- **Saturation:** Colas de espera, peticiones pendientes.
- **Errors:** Errores del sistema (ej: fallos de E/S).

**Regla de acción:** Si una métrica excede un umbral (ej: error rate > 5% en 5 minutos), el agente DEBE haber configurado una alerta o al menos un log de advertencia.

**Verificación:** ¿Tu servicio expone métricas de Rate, Errors y Duration? Si no, no puedes saber si está funcionando correctamente en producción. Hazlo.

---

## Principio fundamental

La observabilidad no es un lujo: es el requisito mínimo para operar software en producción sin adivinar. Un sistema sin logs estructurados, sin métricas y sin trazabilidad es un sistema ciego. La resiliencia no es una opción: es la garantía de que el sistema no colapsará ante un fallo predecible. El agente debe diseñar e implementar sistemas que puedan ser monitoreados, depurados y recuperados por humanos y por otros sistemas. Si no puedes ver qué está pasando, no puedes arreglarlo.
