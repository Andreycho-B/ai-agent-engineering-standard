# 22. TESTING ESTRATÉGICO

**Versión:** 2.0  
**Estado:** Normativo  
**Jerarquía:** Nivel 3 (Especializaciones)

---

## Propósito

Define la estrategia de pruebas que el agente debe aplicar para garantizar que el sistema funciona correctamente, es resistente a regresiones y puede evolucionar con confianza. No se trata de escribir todas las pruebas posibles, sino de escribir las pruebas **correctas** en el **lugar correcto** y con la **profundidad adecuada**. Las pruebas son una herramienta de ingeniería, no un ritual de cobertura.

Este documento se integra con el **Protocolo Operativo (01)** (donde se ejecutan las intervenciones), la **Conciencia del Proyecto (09)** (para comprender el contexto y las dependencias), la **IA Generativa (13)** (para evitar sesgos), el **Backend (16)** , la **Arquitectura (17)** , la **Base de Datos (18)** , las **APIs (19)** y el **Frontend (15)** (donde se implementan las pruebas), los **Principios de Ingeniería Avanzada (23)** (para aplicar TDD con criterio), la **Observabilidad (21)** (para validar que los sistemas son testeables y monitoreables) y la **Memoria del Proyecto (24)** (para registrar fallos y decisiones de testing).

## TST-001 — Pirámide de Pruebas (Proporcionalidad)

**Prioridad:** CRÍTICA

**Regla:** El agente debe estructurar las pruebas según la pirámide clásica, con énfasis en la base:

- **Pruebas Unitarias (~70%):** Rápidas, aisladas, sin dependencias externas (BD, APIs, red). Prueban lógica de negocio, cálculos, validaciones y transformaciones de datos.
- **Pruebas de Integración (~20%):** Verifican la interacción entre componentes (ej: servicio + repositorio real, controlador + servicio). Utilizan dependencias reales o embebidas (ej: H2, Testcontainers), pero no el entorno de producción.
- **Pruebas End-to-End (E2E) (~10%):** Flujos completos del usuario (ej: registro → login → crear pedido → pagar). Se ejecutan en un entorno lo más parecido a producción y son más lentas y frágiles. Solo se escriben para flujos críticos (happy path + errores principales).

**Regla de proporción:** Un cambio en el código DEBERÁ ir acompañado de pruebas en el nivel correspondiente. No se escribe una prueba E2E para validar una fórmula matemática (es unitaria), ni una prueba unitaria para verificar que la base de datos persiste correctamente (es integración).

**Verificación:** ¿La mayoría de las pruebas son unitarias (rápidas)? Si el 50% o más son E2E o de integración, la pirámide está invertida y se debe reestructurar.

## TST-002 — Qué probar y qué no probar

**Prioridad:** CRÍTICA

**Regla:** El agente NO DEBE probar:
- Frameworks o librerías externas (ej: no probar que `express.json()` funciona).
- Código generado (ej: migraciones de ORM, DTOs planos sin lógica).
- Getters/Setters triviales sin lógica.
- Configuraciones (variables de entorno) — se validan en el arranque, no en pruebas unitarias.

El agente DEBE probar:
- **Lógica de negocio (dominio):** Cálculos, reglas de negocio, invariantes, transiciones de estado.
- **Validaciones:** Campos obligatorios, formatos, límites, reglas de negocio asociadas a datos de entrada.
- **Mapeos y transformaciones:** Cuando un DTO se transforma en una entidad o viceversa, y existe lógica en esa transformación.
- **Manejo de errores:** Excepciones lanzadas, códigos HTTP correctos, mensajes de error en respuestas.
- **Casos límite:** Null, valores vacíos, colecciones vacías, números negativos, máximos, mínimos.
- **Casos de integración:** Consultas SQL complejas, transacciones, interacción con APIs externas (con mocks o stubs controlados).
- **Regresiones:** Cualquier bug que haya sido corregido debe tener una prueba que lo capture si vuelve a aparecer.

**Verificación:** Antes de entregar, revisa tus pruebas: ¿cubren todos los puntos de la lista "DEBE probar" que son aplicables a tu cambio? Si te falta alguno, añádelo. Si tienes pruebas que caen en "NO DEBE probar", elimínalas.

## TST-003 — Mocks y Stubs: cuándo y cómo

**Prioridad:** ALTA

**Regla:** El agente DEBE usar mocks o stubs para aislar la unidad bajo prueba de dependencias externas (BD, APIs, colas, servicios de terceros). Sin embargo, la cantidad y profundidad de los mocks debe ser controlada:

| Dependencia | Estrategia recomendada |
| :--- | :--- |
| **Repositorio (BD)** | Mockear en unitarias; usar BD real (embebida o contenedor) en integración. |
| **Cliente HTTP externo** | Mockear siempre en unitarias; usar stubs controlados en integración. |
| **Colas / Mensajería** | Mockear en unitarias; usar un broker embebido en integración (ej: RabbitMQ en memoria). |
| **Sistema de archivos** | Mockear (ej: usar `MemoryStream` o `VirtualFileSystem`) en unitarias. |
| **Servicios internos del mismo proyecto** | Si son lógica de negocio pura, instanciarlos directamente (sin mock). Si son infraestructura, mockearlos para aislar el SUT. |

**Regla de oro:** Si el mock es más complejo que el código que estás probando, probablemente estás probando en el nivel incorrecto (demasiado abajo o demasiado mockeado). Prefiere pruebas de integración con dependencias reales en lugar de mocks complejos que intentan simular comportamientos difíciles.

**Verificación:** Tus pruebas unitarias deben ejecutarse en < 100 ms cada una. Si una prueba unitaria es lenta, probablemente estás usando dependencias reales donde deberías usar mocks. Si una prueba tiene 10 mocks y 20 configuraciones, es una prueba frágil y mal diseñada.

## TST-004 — Pruebas de Contrato (APIs)

**Prioridad:** CRÍTICA

**Regla:** Para APIs públicas, el agente DEBE implementar pruebas de contrato que validen que la respuesta cumple con la especificación (OpenAPI/Swagger). Estas pruebas deben verificar:

- Códigos de estado HTTP para casos de éxito y error.
- Estructura de la respuesta (campos obligatorios, tipos, formatos).
- Headers (Content-Type, CORS, autenticación).
- Compatibilidad hacia atrás (si se modifica una API existente, no debe romper contratos previos).

**Recomendación:** Usar herramientas como `Pact`, `Dredd` o `Schemathesis` si el proyecto las soporta. En su defecto, al menos una prueba de integración que valide un endpoint contra la especificación.

**Verificación:** Si has modificado un endpoint, ¿has actualizado su documentación OpenAPI? Si no, hazlo. ¿Has probado que la respuesta cumple con el esquema definido? Si no, añade una prueba de contrato.

## TST-005 — Testing en Frontend (Componentes)

**Prioridad:** ALTA

**Regla:** El agente debe priorizar las siguientes estrategias en frontend, alineadas con la pirámide:

1. **Pruebas unitarias de lógica pura:** Funciones helper, utilidades de formato, validaciones de formularios (sin DOM).
2. **Pruebas de componentes aislados:** Renderizado condicional, eventos básicos, props. NO se prueba el estilo visual (colores, padding) en pruebas automatizadas.
3. **Pruebas de integración de flujos:** Flujos completos de páginas (ej: login → redirección) usando `Testing Library` + `Playwright` (E2E) o `JSDOM` (integración).

**Qué NO probar en frontend:**
- Detalles de implementación (estados internos de React, clases CSS específicas).
- La animación o el estilo exacto.
- El funcionamiento de librerías externas (ej: `react-router`).

**Verificación:** Si tu prueba de frontend falla por un cambio de CSS (ej: cambiar un classname), es una mala prueba. Refactorízala para buscar comportamiento visible (texto, atributos `aria-*`, roles) en lugar de selectores CSS.

## TST-006 — Cobertura: métrica útil, no meta

**Prioridad:** ALTA

**Regla:** La cobertura de código es una **herramienta de diagnóstico**, no un objetivo de entrega. El agente DEBE:

- Usar cobertura para **identificar áreas no probadas** (especialmente lógica de negocio y manejo de errores).
- NO perseguir cobertura del 100% si eso implica probar getters/setters o código trivial.
- Asegurarse de que las partes críticas (dominio, seguridad, cálculos financieros) tengan cobertura > 90%.
- Aceptar cobertura baja en capas de infraestructura (configuraciones, mapeadores automáticos) si están probadas indirectamente por pruebas de integración.

**Verificación:** Si has reducido la cobertura en una parte crítica, ¿está justificado? Si no, añade pruebas. Si tu cobertura ha subido pero solo probaste código trivial, no es una mejora real.

## TST-007 — TDD: Cuándo usarlo y cuándo no

**Prioridad:** MEDIA

**Regla:** El agente DEBERÍA aplicar TDD (escribir la prueba antes del código) en los siguientes casos:
- **Lógica de dominio compleja:** Reglas de negocio con múltiples casos límite y estados.
- **Corrección de bugs:** Escribir una prueba que reproduce el bug, luego corregir el código y verificar que la prueba pasa (evita regresiones).
- **APIs críticas:** Diseñar el contrato primero (prueba de aceptación), luego implementar.

El agente NO DEBE aplicar TDD rígidamente en:
- **Prototipos o exploración:** Cuando el diseño aún no está claro.
- **Refactorizaciones que no cambian comportamiento:** Ya existen pruebas; solo se reestructura el código.
- **Código de infraestructura:** Configuraciones, migraciones, scripts de despliegue.

**Verificación:** Si has escrito código sin pruebas, y la lógica es compleja, estás en deuda técnica. Si has escrito pruebas antes de código para una funcionalidad simple, estás sobreingeniando. Aplica TDD con criterio.

## TST-008 — Pipeline de CI/CD como Gate de Calidad Bloqueante

**Prioridad:** CRÍTICA

**Regla:** El agente **DEBERÁ** definir el pipeline de CI/CD como un **gate de calidad bloqueante**. El pipeline **DEBERÁ** incluir, como mínimo, las siguientes etapas en orden estricto:

1. Análisis estático (Linter / Formatter).
2. Pruebas unitarias (rápidas).
3. Pruebas de integración (con BD y dependencias reales embebidas).
4. Pruebas E2E (flujos críticos).
5. Análisis de seguridad SAST (según `SEC-009`).
6. Pruebas de mutación (para módulos críticos, según `TST-010`).

Si cualquiera de estas etapas falla, el agente **NO PODRÁ** fusionar (merge) los cambios. El pipeline **NO DEBERÁ** ser desactivado para acelerar la entrega. La única excepción es una justificación documentada en el `DECISION_LOG.md` (13) que demuestre que la falla es un falso positivo y que el equipo de QA ha sido notificado.

**Verificación:** Antes de realizar el push final, el agente debe verificar que todas las etapas del pipeline han pasado en el entorno de CI. Si alguna ha fallado, se debe corregir el código o la prueba. No se permite el "merge force".

## TST-009 — Pruebas de Rendimiento y Carga (Escalabilidad)

**Prioridad:** MEDIA

**Regla:** El agente DEBE considerar pruebas de rendimiento cuando el cambio afecta a:
- Endpoints críticos con alta concurrencia esperada (> 100 req/seg).
- Consultas a base de datos que pueden volverse lentas con el crecimiento de datos.
- Procesos batch o asíncronos que procesan grandes volúmenes de datos.

**Acción recomendada:** Incluir una prueba de carga simple (ej: usando `k6` o `Artillery`) que verifique que el endpoint responde en < 300 ms bajo carga esperada. Si no es posible, al menos documentar la estimación de rendimiento y los cuellos de botella potenciales.

**Verificación:** Si tu cambio añade una nueva consulta SQL, ¿has verificado que tiene índices y que se ejecuta en menos de 100 ms con datos de prueba representativos? Si no, es una deuda de rendimiento.

## TST-010 — Pruebas de Mutación (Mutation Testing)

**Prioridad:** ALTA

**Regla:** Cuando el dominio requiera alta fiabilidad (ej: módulos financieros, de seguridad, o lógica de negocio crítica), el agente **DEBERÁ** ejecutar pruebas de mutación sobre la lógica de dominio y las reglas de negocio. 

El sistema de mutación debe modificar el código fuente (ej: invertir condiciones, cambiar operadores, eliminar líneas) y verificar si el conjunto de pruebas unitarias falla. Si el conjunto de pruebas no detecta la mutación (la mutación "sobrevive"), el agente **DEBERÁ** añadir nuevas pruebas que cubran el caso límite no detectado.

**Excepciones:** Proyectos con alta rotación de código prototipo, sin lógica de negocio compleja, o donde la herramienta de mutación no esté disponible para el stack tecnológico del proyecto.

**Verificación:** Antes de la auditoría final (`AUD-003`), el agente debe ejecutar la herramienta de mutación (ej: PITest, Stryker, Mutmut) y garantizar que la **tasa de mutación superviviente sea inferior al 5%** en los módulos críticos. Si supera el umbral, el código no se entrega hasta que se añadan las pruebas faltantes.

## TST-011 — Pruebas de Aceptación y Regresión Semántica (UAT)

**Prioridad:** ALTA

**Regla:** Para cambios de alto impacto (nuevas funcionalidades o reestructuraciones profundas), el agente **DEBERÁ** generar un conjunto de pruebas de aceptación que validen los flujos de negocio desde la perspectiva del usuario final. Estas pruebas actúan como un **contrato semántico**. 

Si el cambio rompe un flujo UAT, se considera una regresión funcional, independientemente de que las pruebas unitarias y de integración pasen. Las pruebas UAT deben ejecutarse en el entorno de staging o integración.

**Excepciones:** Cambios de refactorización pura (sin alteración de la lógica de negocio) y bugfixes menores sin alteración de flujos de usuario.

**Verificación:** El agente debe ejecutar la suite de UAT y garantizar que el 100% de los escenarios de usuario críticos (happy paths y principales errores) pasan antes de la entrega.

---

## Principio fundamental

El testing no es una actividad separada del desarrollo; es parte integral del diseño. Una arquitectura que es difícil de probar es una mala arquitectura (viola la "D" de SOLID y el principio de inversión de dependencias). El agente debe escribir pruebas que sean rápidas, deterministas y que verifiquen el comportamiento observable, no los detalles de implementación. Las pruebas son el seguro contra la entropía: permiten evolucionar el sistema con confianza. Escribir pruebas es una inversión, no un coste.
