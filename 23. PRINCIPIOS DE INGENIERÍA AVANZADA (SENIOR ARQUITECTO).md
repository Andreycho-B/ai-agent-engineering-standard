**Estado:** Normativo  
**Jerarquía:** Nivel 3 (Especializaciones)

## Propósito

Este documento actúa como puente entre los principios abstractos de la ingeniería de software y las reglas concretas del estándar. Define **matrices de decisión** para que el agente sepa cuándo aplicar DDD, Arquitectura Hexagonal o SOLID, y cuándo es mejor quedarse con CRUD plano, capas simples o YAGNI. La sofisticación técnica debe ser proporcional a la complejidad del dominio, no a una preferencia estilística.

Este documento se integra con el **Protocolo Operativo (01)** (donde se ejecutan las decisiones), la **Conciencia del Proyecto (09)** (para comprender el contexto actual), la **IA Generativa (13)** (para evitar sesgos), el **Backend (16)** , la **Arquitectura (17)** , la **Base de Datos (18)** , las **APIs (19)** y el **Frontend (15)** (donde se aplican estos principios), el **Testing Estratégico (22)** (para validar las decisiones de diseño), la **Observabilidad (21)** (para monitorear el impacto de las decisiones) y la **Memoria del Proyecto (24)** (para registrar decisiones arquitectónicas avanzadas).

## AV-001 — Matriz de Decisión: DDD (Táctico) vs. CRUD Transaccional

**Prioridad:** CRÍTICA

**Regla:** El agente debe elegir entre un enfoque CRUD (Modelo de Datos simple + Servicios Anémicos) y DDD Táctico (Agregados, Objetos de Valor, Eventos de Dominio) basándose en la siguiente matriz de decisión.

**Tabla de Decisión:**

| Criterio | ✅ CRUD (Simple) | ✅ DDD Táctico (Complejo) |
| :--- | :--- | :--- |
| **Complejidad de la Lógica** | Principalmente consultas y actualizaciones directas (CRUD puro). | Reglas de negocio complejas, con múltiples estados transicionales (ej: préstamos, facturación, logística). |
| **Cambios Frecuentes** | La lógica es estable y no se esperan cambios profundos. | El negocio cambia constantemente y la lógica debe ser fácilmente modificable sin romper todo. |
| **Invariantes** | Pocas invariantes (solo unicidad y validaciones básicas). | Múltiples invariantes que deben cumplirse siempre (ej: saldo no negativo, stock reservado). |
| **Equipo/Tamaño** | Proyecto pequeño, < 5 módulos. | Proyecto grande, > 10 módulos, varios equipos trabajando. |
| **Herencia / Legacy** | Proyecto nuevo desde cero o legacy simple. | Se necesita encapsular lógica heredada compleja en modelos de dominio puros. |

**Regla de aplicación:**
- **Si la mayoría de los criterios apuntan a CRUD**, el agente **DEBERÁ** usar modelos de datos planos (EJ: Entidades de DB mapeadas directamente a DTOs) y servicios delgados.
- **Si la mayoría de los criterios apuntan a DDD**, el agente **DEBERÁ** implementar **Agregados** (raíces que garantizan invariantes), **Objetos de Valor** (inmutables) y **Eventos de Dominio** (para desacoplar efectos secundarios).

**Verificación:** ¿Estás usando DDD en un proyecto CRUD? Si es así, es sobreingeniería. ¿Estás usando CRUD en un proyecto con reglas contables complejas? Si es así, es infradiseño.

## AV-002 — Matriz de Decisión: Arquitectura Hexagonal/Clean vs. Capas Planas

**Prioridad:** CRÍTICA

**Regla:** El agente debe decidir si introduce puertos y adaptadores (Hexagonal) o capas planas (Controlador → Servicio → Repositorio) según la siguiente matriz.

**Tabla de Decisión:**

| Criterio | ✅ Capas Planas | ✅ Hexagonal / Clean |
| :--- | :--- | :--- |
| **Infraestructura cambiante** | BD, colas, APIs externas son fijas y no se prevén cambios. | Se prevé cambiar de BD (SQL a NoSQL) o de proveedor de cloud. |
| **Lógica de negocio pura** | El negocio está altamente acoplado a la BD (Stored Procedures, lógica en vistas). | La lógica de negocio es compleja y debe ser testeable aisladamente sin BD. |
| **Tamaño del equipo** | 1-3 developers. | > 5 developers o varios equipos. |
| **Testing** | Pruebas de integración suficientes. | Se requieren pruebas unitarias de alta velocidad (> 1000) sin levantar infraestructura. |

**Regla de aplicación:**
- **Si los criterios apuntan a Capas Planas**, el agente **DEBERÁ** mantener la inyección de dependencias simple y los repositorios directamente conectados a la BD.
- **Si los criterios apuntan a Hexagonal**, el agente **DEBERÁ** definir **Puertos** (interfaces para la lógica de negocio) y **Adaptadores** (implementaciones específicas de infraestructura) para que el dominio no dependa de nada externo (aplicando el **Dependency Inversion Principle** de SOLID).

**Verificación:** ¿Has añadido interfaces y puertos "por si acaso" sin justificación real? Si es así, simplifica. ¿Estás atado a una BD específica y es difícil hacer pruebas? Si es así, introduce el puerto.

## AV-003 — Principios SOLID a Nivel Arquitectónico

**Prioridad:** ALTA

**Regla:** El agente debe aplicar SOLID como filtro de calidad, pero nunca como un dogma que justifique capas vacías. Cada principio debe verificarse con una pregunta específica:

| Principio | Pregunta de Verificación Arquitectónica | Violación común (IA Slop) |
| :--- | :--- | :--- |
| **S (Responsabilidad Única)** | ¿Este módulo/capa tiene exactamente una razón para cambiar? | Servicios que manejan lógica de negocio, envían emails y generan PDFs. |
| **O (Abierto/Cerrado)** | ¿Puedo extender comportamiento sin modificar el código central? (Polimorfismo / Estrategias) | Añadir `if (tipo == "A")` en lugar de usar herencia/estrategia cuando hay 3+ variantes. |
| **L (Sustitución de Liskov)** | ¿Puedo reemplazar una implementación concreta por otra sin romper reglas? | Implementar un `FakeRepository` que simula datos, pero que no lanza las mismas excepciones que el real. |
| **I (Segregación de Interfaces)** | ¿Las interfaces son pequeñas y específicas para el cliente que las usa? | Interfaces gigantes con métodos `Get`, `Update`, `Delete`, `SendEmail`, `ExportPDF` (dependencias forzadas). |
| **D (Inversión de Dependencias)** | ¿Los módulos de alto nivel dependen de abstracciones, no de detalles concretos? | El controlador instancia directamente el repositorio con `new` (dependencia rígida). |

**Regla de oro:** Si implementar SOLID requiere crear una **capa vacía** (una interfaz con una única implementación que solo delega), es preferible **no aplicar** ese principio hasta que exista una segunda implementación real (YAGNI).

**Verificación:** Revisa tu diseño final. ¿Cada elemento SOLID implementado tiene una justificación tangible (2+ implementaciones, casos de prueba, extensibilidad demostrada)? Si no, revísalo.

## AV-004 — DRY, KISS, YAGNI (Operativos)

**Prioridad:** CRÍTICA

**Regla:** Estos tres principios deben aplicarse en orden de prioridad estricto cuando entran en conflicto:

1. **KISS (Keep It Simple, Stupid)** — **Prioridad #1**. La solución más simple que funciona correctamente es la mejor. Si una solución es compleja de entender, es mala, aunque sea "muy elegante" o "escalable".
2. **YAGNI (You Aren't Gonna Need It)** — **Prioridad #2**. No añadas funcionalidad, flexibilidad, parámetros o abstracciones "para el futuro". El futuro casi nunca es el que imaginas. Si no se necesita HOY, no se implementa HOY.
3. **DRY (Don't Repeat Yourself)** — **Prioridad #3**. Solo se aplica cuando la duplicación implica **lógica de negocio** o **invariantes**. La duplicación sintáctica (escribir las mismas 2 líneas de SQL o el mismo mapeo de objetos) es aceptable y preferible a crear una abstracción que aísle esas líneas si aún no hay una tercera repetición.

**Regla de conflicto:**
- Si DRY exige crear una abstracción compleja, pero KISS dice que la duplicación es simple -> **Gana KISS**. Duplica, luego refactoriza cuando aparezca la tercera ocurrencia.
- Si YAGNI dice "no necesito esto ahora", pero DRY dice "esto está duplicado en 5 sitios" -> **Gana DRY** (porque la repetición de lógica de negocio ya es un problema presente).

**Verificación:** Antes de crear una abstracción para reutilizar código, pregúntate: ¿Cuántas veces se repite? Si es < 3, y la abstracción requiere más de 2 parámetros o lógica condicional, es mejor duplicar (KISS).

## AV-005 — BICEP (Casos de Prueba)

**Prioridad:** ALTA

**Regla:** BICEP es un acrónimo para asegurar que las pruebas cubren las dimensiones críticas del dominio. El agente debe usarlo para verificar su diseño antes de entregar.

| Letra | Significado | Pregunta de Verificación |
| :--- | :--- | :--- |
| **B** | **Boundary** (Límites) | ¿Qué pasa con valores en el límite (0, null, empty, max length)? |
| **I** | **Inverse** (Inversa) | ¿Puedo probar la operación inversa para verificar consistencia (ej: Guardar -> Leer -> Comparar)? |
| **C** | **Cross-check** (Cruzada) | ¿Puedo verificar el resultado usando un método alternativo (ej: usar otra función para calcular el total)? |
| **E** | **Error conditions** (Errores) | ¿Qué pasa con excepciones, timeouts, BD caída? |
| **P** | **Performance** (Rendimiento) | ¿Qué pasa con grandes volúmenes de datos (ej: 10,000 registros)? |

Si el diseño no permite responder fácilmente a estas preguntas (ej: no se puede mockear la BD para probar errores), el agente debe reconsiderar el diseño aplicando AV-002 (Hexagonal) o AV-003 (Dependency Inversion).

## AV-006 — La Trampa de la Sobreingeniería (Indicadores de Alarma)

**Prioridad:** CRÍTICA

**Regla:** El agente debe detenerse y simplificar inmediatamente si detecta **2 o más** de estos indicadores en su implementación:

1. **Interfaces con una única implementación** que no sea para pruebas.
2. **Carpetas o capas que solo contienen 1 archivo** y no se espera que crezcan.
3. **Patrones de diseño** (Factory, Strategy, Builder, etc.) usados para resolver lógica que podría ser un simple `if/else`.
4. **Configuraciones excesivas** (más de 3 variables de entorno para una funcionalidad simple).
5. **Arquitectura de microservicios** en un proyecto que podría ser un monolito manejable.
6. **Uso de DDD (Agregados, Eventos)** para entidades que no tienen invariantes complejas (son básicamente tablas).
7. **Código genérico** (ej: `TEntity`, `IRepository<T>`) cuando solo hay 2 o 3 entidades.

**Verificación:** Revisa tu entrega final. ¿Cuántos indicadores de esta lista aparecen? Si hay 2 o más, simplifica antes de entregar.

## AV-007 — Límite de complejidad ciclomática y mantenibilidad
| :--- |
| **Prioridad:** ALTA |
| **Regla:** El agente **DEBERÁ** medir la complejidad ciclomática (CC) y el índice de mantenibilidad de cualquier nueva función, método o componente. Si una función supera una CC de 10 o el componente supera un índice de mantenibilidad < 65 (según la escala estándar de Microsoft o similar), la implementación se considera excesivamente compleja y **DEBERÁ** ser refactorizada. La complejidad cognitiva debe ser medible, no subjetiva. |
| **Excepciones:** Funciones generadas automáticamente por frameworks (ej: mapeadores) o código estrictamente de configuración. |
| **Verificación:** Antes de `OP-005` (Simplificación), el agente debe haber ejecutado un analizador de complejidad (ej: `radon`, `eslint complexity`, `sonar`) y garantizar que el código nuevo cumple el umbral. |

## Principio fundamental

Un ingeniero senior no se define por la cantidad de patrones que conoce, sino por su **capacidad para no usar un patrón cuando no es necesario**. La sobreingeniería es deuda técnica disfrazada de sofisticación. El agente debe aplicar la sofisticación técnica solo cuando la complejidad del dominio la exija. En caso de duda, elige la opción más simple y documenta los trade-offs. El código fácil de eliminar o refactorizar es mejor que el código difícil de entender.
