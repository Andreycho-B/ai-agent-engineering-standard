# 30. POLÍTICA DE CONTROL DE VERSIONES Y SEGURIDAD DE LA INFORMACIÓN (GIT/GITHUB)

**Versión:** 1.0  
**Estado:** Normativo  
**Jerarquía:** Nivel 5 (Gobernanza)

---

## Propósito

Define las restricciones y buenas prácticas que el agente debe aplicar al interactuar con sistemas de control de versiones (Git) y plataformas de alojamiento (GitHub, GitLab, etc.). El objetivo es prevenir la exposición accidental de información sensible (secretos, claves, logs, diálogos internos, arquitectura privada) y garantizar que los commits sean atómicos, descriptivos y seguros. Esta política se integra con los principios de **Seguridad (20)** y **Memoria del Proyecto (24)** , y es de aplicación obligatoria en toda operación que involucre `git add`, `git commit`, `git push` o la gestión de credenciales.

---

## GIT-001 — Archivos de exclusión obligatorios (.gitignore y .agentignore)

**Prioridad:** CRÍTICA

**Regla:** Todo repositorio DEBE contener al menos un archivo `.gitignore` y un archivo `.agentignore` en su raíz. El agente DEBE respetar estrictamente ambos archivos y NO DEBE añadir, modificar o eliminar archivos que estén listados en ellos.

- **`.gitignore`**: Debe incluir, como mínimo:
  - Archivos de entorno (`.env`, `.env.*`, `*.secret`).
  - Archivos de claves y certificados (`*.pem`, `*.key`, `*.cer`, `*.crt`).
  - Archivos de logs (`*.log`, `logs/`).
  - Archivos de dependencias y paquetes (`.venv/`, `node_modules/`, `vendor/`, `__pycache__/`).
  - Archivos de configuración local (`.vscode/`, `.idea/`, `*.local`).
  - Archivos de pruebas no relevantes (`coverage/`, `*.test.log`).
  - Archivos de sistema (`.DS_Store`, `Thumbs.db`).

- **`.agentignore`**: Debe incluir, como mínimo, todos los patrones de `.gitignore`, más los específicos para el agente:
  - Archivos de diálogo o conversación (`*_dialog.md`, `*_chat.log`, `conversation_*.txt`).
  - Archivos temporales del agente (`*.tmp`, `*.cache`, `*.draft`).
  - Archivos de contexto sensible (READMEs internos que contienen arquitectura detallada, diagramas de red, o credenciales de prueba).
  - Archivos de configuración de pruebas que contengan datos de producción (datos de staging o producción anonimizados).

**Verificación:** Antes de cada commit, el agente DEBE ejecutar `git status` y verificar que ningún archivo listado en `.gitignore` o `.agentignore` esté siendo añadido. Si aparece alguno, el agente DEBE detener el commit y corregir la situación.

## GIT-002 — Prohibición absoluta de secretos en el repositorio

**Prioridad:** CRÍTICA

**Regla:** Está terminantemente prohibido almacenar cualquier tipo de secreto, clave, token o credencial en el código fuente o en cualquier archivo dentro del repositorio. Esto incluye, pero no se limita a:

- Variables de entorno de producción (`.env`, `.env.production`, etc.).
- Claves API de servicios de pago, bases de datos, o servicios en la nube.
- Claves privadas criptográficas (`*.pem`, `*.key`, `*.cer`, `*.pkcs12`).
- Tokens de acceso a repositorios, registries de contenedores, o plataformas de despliegue.
- Contraseñas de usuarios o sistemas.
- Certificados digitales.
- Cualquier información que, si se filtrara, comprometiera la seguridad del sistema o de los usuarios.

**Excepción:** Los secretos pueden ser referenciados mediante variables de entorno o utilizando un sistema de gestión de secretos (como HashiCorp Vault, AWS Secrets Manager, GitHub Secrets). El agente DEBE usar estas referencias y nunca el valor literal.

**Verificación:** El agente DEBE ejecutar herramientas de escaneo de secretos (como `trufflehog`, `gitleaks`, o `git-secrets`) antes de cada `git push`. Si se detecta un secreto, el agente DEBE detener la operación y eliminar el secreto del historial (usando `git filter-branch` o BFG Repo-Cleaner).

## GIT-003 — Política de commits: atómicos, descriptivos y firmados

**Prioridad:** ALTA

**Regla:** Cada commit DEBE cumplir con los siguientes estándares de calidad:

1. **Atomicidad:** Cada commit DEBE contener un único cambio lógico. No se deben mezclar correcciones de errores con nuevas funcionalidades, ni cambios de estilo con cambios de comportamiento.
2. **Mensaje descriptivo:** El mensaje del commit DEBE seguir el formato estándar: `<tipo>(<alcance>): <descripción breve>`.
   - Tipos permitidos: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `chore`, `revert`.
   - Ejemplo: `feat(auth): add JWT refresh token rotation`.
   - El cuerpo del mensaje (opcional) DEBE explicar el *por qué* del cambio, no solo el *qué*.
3. **Firma:** En proyectos que lo requieran, los commits DEBEN estar firmados con GPG (GitHub: `-S` flag) para verificar la autoría.
4. **Tamaño:** Un commit NO DEBE superar las 400 líneas modificadas (a menos que sea una refactorización masiva justificada). Si excede, el agente DEBE dividirlo en varios commits atómicos.

**Verificación:** Antes de `git commit`, el agente DEBE revisar el diff y verificar que cumple con la atomicidad y el tamaño. Si no, debe dividir el commit.

## GIT-004 — Prohibición de subir archivos de diálogo, pruebas locales y logs

**Prioridad:** CRÍTICA

**Regla:** El agente NO DEBE subir bajo ningún concepto los siguientes tipos de archivos al repositorio:

- Archivos de diálogo o conversaciones mantenidas con el usuario o con otros agentes (`*_dialog.md`, `*_chat.log`, `conversation_*.txt`, `*_prompt_*.md`).
- Archivos de pruebas que contengan datos de producción o que expongan lógica interna sensible (`*_test_secret_data.json`, `*_test_pii.csv`).
- Archivos de logs (`*.log`, `logs/`, `*.out`, `*.err`) que puedan contener información de depuración con datos de usuario o stack traces internos.
- Archivos de configuración de herramientas que revelen rutas internas, servidores o estrategias de despliegue (`*.toml`, `*.yaml`, `*.json` que contengan URLs internas o nombres de hosts).

**Verificación:** El agente DEBE ejecutar `git diff --name-only` para revisar qué archivos van a ser añadidos. Si encuentra alguno de estos patrones, DEBE detener el commit y eliminarlos del staging (`git rm --cached`).

## GIT-005 — Principio de menor privilegio para credenciales y tokens

**Prioridad:** CRÍTICA

**Regla:** El agente DEBE operar bajo el principio de menor privilegio al utilizar credenciales o tokens de acceso a plataformas (GitHub, AWS, etc.). Esto implica:

- No usar tokens con permisos de administrador o de escritura total a menos que sea estrictamente necesario.
- Los tokens DEBEN estar limitados a repositorios específicos o a acciones concretas (ej: solo lectura, solo push a ramas específicas).
- Los tokens DEBEN tener una fecha de expiración definida.
- Nunca compartir tokens entre proyectos o contextos.

**Verificación:** El agente DEBE verificar, antes de cada `push`, que el token utilizado tiene el alcance mínimo necesario. Si tiene permisos excesivos, DEBE solicitar un token con menor privilegio.

## GIT-006 — Protección contra inyección de instrucciones (Prompt Injection) en comandos Git

**Prioridad:** CRÍTICA

**Regla:** El agente NO DEBE ejecutar comandos de Git que incluyan directamente entradas del usuario sin sanitización. Si el usuario solicita algo como `git commit -m "mensaje del usuario"`, el agente DEBE sanitizar el mensaje para evitar inyecciones (ej: escapando caracteres especiales como `;`, `|`, `$`, `\n`). Nunca construir comandos de shell con concatenación directa de strings sin validación.

**Excepción:** Solo se permite ejecutar comandos de Git proporcionados por el usuario si el usuario tiene permisos de administrador explícitos y el comando es revisado por un segundo agente o por el protocolo de revisión de seguridad (ver **25. Sistema de Auditoría**).

**Verificación:** Antes de ejecutar cualquier comando Git que dependa de entrada del usuario, el agente DEBE validar y escapar la entrada. Si hay duda, DEBE consultar al usuario o al equipo.

## GIT-007 — Revisión pre-commit y auditoría de cambios

**Prioridad:** ALTA

**Regla:** Antes de cada commit, el agente DEBE ejecutar una revisión manual (o automatizada) de los cambios para asegurar que:

1. No se están añadiendo secretos (GIT-002).
2. No se están subiendo archivos prohibidos (GIT-001, GIT-004).
3. Los commits son atómicos y tienen mensajes adecuados (GIT-003).
4. No se están modificando archivos de configuración de terceros sin justificación.

**Verificación:** El agente DEBE utilizar `git diff --cached` para inspeccionar el staging antes de commit. Si encuentra algo sospechoso, DEBE detenerse y notificar al usuario.

---

## Principio fundamental

El control de versiones es la memoria del proyecto. La seguridad de esa memoria es tan importante como la seguridad del código mismo. Un solo secreto filtrado puede comprometer todo el sistema. Un solo commit mal redactado puede confundir al equipo y generar deuda técnica. El agente debe tratar cada `git add` y cada `git commit` como una operación crítica, revisada y verificada, aplicando el principio de "confianza cero" a cualquier dato que vaya a ser persistido en el repositorio.
